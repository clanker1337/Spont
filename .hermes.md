# Spont Project Instructions

## Product

Spont is a worldwide, location-aware spontaneous-plan generator.

It returns exactly three actionable plans that fit the user’s:

* Starting location
* Available time
* Maximum travel time
* Transportation mode
* Budget
* Indoor/outdoor preference
* Energy level
* Activity preferences
* Group size
* Current weather and opening conditions

The product is not a generic nearby-business directory.

## MVP boundaries

The MVP includes:

* Browser geolocation
* Manual location entry
* Map-point selection
* Nearby-place discovery
* Opening-hours filtering
* Budget and duration constraints
* Actual travel-time estimates
* Weather-aware filtering and scoring
* Exactly three diverse single-destination plans
* External navigation links
* Demo mode without API credentials

The MVP excludes:

* User accounts
* Social functionality
* Reservations or purchases
* Worldwide transit routing
* Multi-day planning
* Multi-stop optimization
* Recommendation history
* Event-site scraping
* AI-generated reviews

Ticketmaster events and lightweight preference history are post-MVP.

## Technology

* SvelteKit
* TypeScript strict mode
* Zod
* Vitest
* Playwright
* Docker
* No database in the MVP

Use the package manager and versions recorded in the repository.

Do not change foundational tooling without an architecture decision record.

## Architecture

Keep these layers separate:

1. User interface
2. Application orchestration
3. Domain models
4. Deterministic filtering and scoring
5. Plan generation
6. Provider interfaces
7. Provider adapters

Provider-specific types must not leak into domain or UI code.

Core ranking, filtering, weather policy, and plan diversity logic must be implemented as deterministic pure functions wherever practical.

An LLM must not select plans from raw provider results.

## Provider rules

Every external provider must have:

* A typed interface
* A live adapter
* A deterministic fixture adapter
* Boundary validation
* Typed error handling
* Timeout behavior
* Tests using saved fixtures

Do not call live APIs in normal unit tests.

Do not commit API keys.

Keep secret keys in server-only environment variables.

Do not use public Nominatim for systematic POI discovery.

## Plan-generation invariants

Normal successful output contains exactly three plans:

1. Best overall
2. Lowest cost or friction
3. Most unusual viable option

Never invent a destination, opening time, event, cost, rating, or travel duration.

Represent uncertainty explicitly.

Hard constraints run before ranking.

Route only shortlisted candidates.

All plans must fit within the user’s total available time.

## GitHub workflow

GitHub issues and pull requests are the authoritative work record.

Before coding:

* Identify the relevant issue.
* Confirm its acceptance criteria.
* Check dependencies and blocking issues.
* Create a focused branch.

Branch format:

`issue-<number>-<short-description>`

Every pull request must:

* Address one coherent issue or tightly related set of sub-issues
* Include `Closes #<issue-number>`
* Describe the implementation
* Report tests run
* Identify risks and limitations
* Include screenshots for UI changes
* Update relevant documentation

Do not push implementation work directly to main.

Do not merge with failing required checks.

Create a follow-up issue for deferred work rather than hiding it in comments or TODOs.

## Required checks

Before declaring work complete, run the repository’s commands for:

* Formatting
* Linting
* Type checking
* Unit tests
* Integration tests
* Production build
* Playwright smoke tests when applicable

Do not report a check as passing unless it was actually executed.

## Coding standards

* Use strict TypeScript.
* Avoid `any`; document unavoidable exceptions.
* Validate external and user-controlled data.
* Prefer small, composable functions.
* Use descriptive domain terminology.
* Keep provider adapters thin.
* Avoid hidden global state.
* Use dependency injection for providers and time.
* Make time-sensitive tests deterministic.
* Test boundary conditions and failure cases.
* Avoid speculative abstractions not required by an issue.

## Privacy and security

* Request geolocation only after an explicit user action.
* Explain why location is requested.
* Support manual location without browser permission.
* Do not persist precise coordinates in the MVP.
* Avoid logging precise coordinates, provider credentials, or sensitive request data.
* Use least-privilege API-key restrictions.
* Treat provider responses as untrusted input.
* Prevent secrets from entering client bundles.
